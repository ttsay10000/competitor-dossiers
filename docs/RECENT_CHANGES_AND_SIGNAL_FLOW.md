## 2. How signals get into the executive summary

Executive summary is generated by:

1. **Route:** `GET /dossier/{competitor_id}/executive-summary`
2. **Context:** `build_dossier_context(session, competitor_id)` → full dossier context (events, snapshots, press, reviews_minimal, social_posts, etc.).
3. **Text for LLM:** `_build_context_text(context)` in `executive_summary.py` builds a single text block from a **subset** of context.
4. **LLM:** `generate_executive_summary(context)` calls the model with that text + system prompt.

### 2.1 What _build_context_text includes today

| Input | Source | Cap / filter |
|-------|--------|---------------|
| Comparison baseline date | context | — |
| New/removed properties | asset_added_since_baseline, asset_removed_since_baseline, asset_delta_by_city | MAX_DELTA_BY_CITY_ROWS = 15 |
| Jobs added/removed + role mix | jobs_*_since_baseline, jobs_by_function, jobs_by_function_property | 12 rows for role mix |
| Recent news | top_news or press_90d | MAX_NEWS_FOR_SUMMARY = 15 |
| Events this week | events_this_week | No cap; all events sent |

### 2.2 What is **not** in the executive summary text (but is in context)

- **reviews_minimal** — Review sentiment per property. In dossier context and template; **not** passed into _build_context_text, so the LLM does not see review data.
- **social_posts** — Raw social posts. In dossier context and template; **not** passed into _build_context_text. Only **narrative.social_signal events** (new executive-relevant posts) are included via events_this_week.

So:

- **Digital footprint (W):** In. Homepage/coming-soon events are in `events_this_week`; labeled in prompt as `[digital footprint]` (all `narrative.*` get that label today; social_signal could be split to `[social]`).
- **Social (S):** In via events. New executive-relevant posts create `narrative.social_signal` events; they appear in `events_this_week` and thus in the summary. Raw social_posts are not in the summary text.
- **Reviews (R):** Not in. Reviews are snapshot-only (no events); reviews_minimal is not added to _build_context_text, so the LLM never sees review sentiment.

### 2.3 Event path and severity

- **Dossier context** (`build_dossier_context`): Loads **all** events in last 90 days (no severity filter), then applies reporting_baseline_date, then builds `events_this_week` = events in last 7 days (no severity filter).
- **Executive summary** (`_build_context_text`): Takes `events_this_week` and sends **all** events to the LLM (no cap). Order is by `occurred_at` or `detected_at` (newest first). `narrative.social_signal` is labeled `[social]`; other `narrative.*` are `[digital footprint]`. Reviews: `reviews_minimal` is included as a "Review sentiment (sample)" block (up to 10 properties).
- **Summary page** (`build_summary_context` for `/dossier/{id}/summary`): Filters to **high/med only** (`e.severity in ("high", "med")`). So the standalone summary page drops low-severity events; the main dossier executive summary does not.

### 2.4 Current caps (so the system doesn’t get overwhelmed)

| Cap | Value | Location |
|-----|--------|-----------|
| Events in summary text | No cap | All events_this_week in executive_summary.py |
| News items in summary text | 15 | MAX_NEWS_FOR_SUMMARY |
| Delta-by-city rows | 15 | MAX_DELTA_BY_CITY_ROWS |
| Role mix rows | 12 | _build_context_text (jobs_by_function + jobs_by_function_property) |
| Location rows (LLM) | 25 | MAX_LOCATION_ROWS_FOR_SUMMARY |

The main control for “not overwhelming” the summary is Events are not capped; all events in the last 7 days are sent. Order is time-based (newest first). You can add sorting/filtering by priority or severity if needed.

## 3. Addressing the codebase and adding prioritization

### 3.1 Gaps to address

1. **Reviews in executive summary**  
   - Option A: Add a short “Review sentiment (sample)” block in _build_context_text from context["reviews_minimal"] (e.g. 1–2 lines per property, capped at 5–10 properties).  
   - Option B: Define a review event type (e.g. narrative.review_trend) when sentiment drops or trend changes; then it flows in via events like other signals.

2. **Social/digital footprint labeling**  
   - In _build_context_text, all `narrative.*` events are labeled `[digital footprint]`. Implemented: `narrative.social_signal` → `[social]`; homepage/coming_soon stay `[digital footprint]`.

3. **Event prioritization (optional)**  
   - Today: take the 8 most recent events (by occurred_at/detected_at).  
   - For “prioritization by signal type”: sort (or filter) events before slicing to 8, e.g. by severity first, then by a per-type priority (e.g. asset.new_market > talent.hiring_surge > narrative.social_signal), then by date. That way high-impact signals are guaranteed to fill the 8 slots when available.

4. **Main page status (T/A/P/W/S/R)**  
   - Plan already calls out: use DISPLAY_CHANNELS and channel→letter map (W=website, S=social, R=reviews) in competitors.html so status line shows all channels.

5. **CLI**  
   - Add `reviews` (and `social` if missing) to `--channel` choices and “all channels” message so cron/CLI can run all signals.

### 3.2 Where to implement signal prioritization

- **Event list for executive summary**  
  - **Where:** In `build_dossier_context` when building `events_this_week`, or in `_build_context_text` when consuming `events_this_week`.  
  - **How:** Define a priority order (e.g. severity: high > med > low; then event type order: asset.new_market, talent.hiring_surge, partner.*, narrative.homepage_updated, narrative.coming_soon, narrative.social_signal, …). Sort `events_this_week` by that priority then by date before passing to `_build_context_text`.  
  - **Alternative:** Keep building events_this_week as-is, but in _build_context_text sort the list by a small priority map (e.g. type → rank) before formatting.

- **Per-signal caps (optional)**  
  - To avoid one signal type dominating: e.g. “at most 3 narrative.* events in the 8” or “at least 1 asset and 1 talent if present”. Can be implemented in the same place as above when building the list for the summary.

- **Severity filter for dossier executive summary (optional)**  
  - To align with the summary page: filter `events_this_week` to high/med before passing to _build_context_text (or before prioritization + cap). That would exclude low-severity events from the main dossier summary.

### 3.3 Suggested next steps

1. **Document** the chosen priority order (by severity and/or event type) and any per-type caps in SIGNALS.md or a short “Executive summary input” section in this doc.  
2. **Implement** sorting (and optional filtering) of `events_this_week` by that priority before passing to `_build_context_text`.  
3. **Optionally** add reviews to the summary: either a compact reviews_minimal block in _build_context_text or a narrative.review_trend event path.  
4. **Optionally** label narrative.social_signal as [social] in _build_context_text and in the system prompt mention “social/post signals” so the model weighs them correctly.  
5. **Wire UI/CLI** for new channels (DISPLAY_CHANNELS, competitors.html W/S/R, CLI channel list) as in the plan.
