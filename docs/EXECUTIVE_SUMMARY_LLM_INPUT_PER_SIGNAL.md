# What Is Sent to the Executive Summary LLM, Per Signal

The executive summary is generated by `generate_executive_summary(context)` in `app/executive_summary.py`. The text the LLM sees is built by `_build_context_text(context)` from the same `context` dict produced by `build_dossier_context()` in `app/routes/dossier.py`.

Below is **what is sent into the LLM per signal** — i.e. which context keys each signal fills and how they appear in the prompt. Events are not capped; all `events_this_week` are sent. Other caps (news, delta rows, review sample) are noted.

---

## 1. Talent

**Context keys used by _build_context_text:**

- `jobs_added_since_baseline` — number (since comparison baseline).
- `jobs_removed_since_baseline` — number.
- `jobs_by_function` — list of `{ function, total, senior }` (business roles).
- `jobs_by_function_property` — same shape (property operations).

**What the LLM sees (exact shape in the prompt):**

- Two lines:  
  `New roles posted since baseline: <N>.`  
  `Roles removed since baseline: <N>.`
- If there are jobs by function: one line like  
  `Current open roles by function (use to interpret significance of new/removed counts): <function>: <total> (<senior> senior); ...`  
  (Up to 12 rows total from `jobs_by_function` + `jobs_by_function_property`; cap is in code.)

**Plus:** Any **talent events** (e.g. `talent.senior_hire_or_role_posted`, `talent.new_capability`, `talent.hiring_surge`) appear in the **Events** section (see §6): for each event, the LLM sees `title [<event_type>]` (e.g. `Senior role posted: VP Strategy [talent.senior_hire_or_role_posted]`).

---

## 2. Asset (properties / footprint)

**Context keys used:**

- `asset_added_since_baseline` — number.
- `asset_removed_since_baseline` — number.
- `asset_delta_by_city` — list of `{ location, added, removed }`.

**What the LLM sees:**

- Two blocks:  
  `New properties: <N> properties in <M> areas — <loc>: <added>; ...`  
  `Removed properties: <N> properties in <M> areas — <loc>: <removed>; ...`  
  (If 0, it sends `New properties: 0.` / `Removed properties: 0.`)
- Delta rows are currently limited by `MAX_DELTA_BY_CITY_ROWS` (15) in code.

**Plus:** Any **asset events** (e.g. `asset.new_market`, `asset.market_exit`, `asset.pipeline_signal`) appear in the **Events** section as `title [<event_type>]`.

---

## 3. Press / news

**Context keys used:**

- `top_news` — preferred; if empty, fallback to `press_90d`.
- `press_90d` — flat list of press items (with date, title, group_title, etc.).

**What the LLM sees:**

- One block:  
  `Recent news (derive bullets from these): (<date>) <title> [<group_title>] | (<date>) ... | ...`  
  (Each item: `(date) title` and optionally `[group_title]`; title truncated to 100 chars in code.)
- Currently limited to `MAX_NEWS_FOR_SUMMARY` (15) items in code.

**Note:** Press does not create “events” in the Events section; it only appears in this Recent news block. Partner/capital/narrative classifications from press can create events (partner.*, capital.*, narrative.*) and those appear in §6.

---

## 4. Digital footprint (website / homepage changes)

**No dedicated context block.** This signal reaches the LLM **only via events**:

- Event types: `narrative.homepage_updated`, `narrative.coming_soon`.
- For each such event, the LLM sees it in the **Events** section as:  
  `title [digital footprint]`  
  (because in code any `narrative.*` type is labeled `[digital footprint]`).

So: **what is sent per digital-footprint signal** = one line per event: `"<event title> [digital footprint]"` in the “Events detected this week” block.

---

## 5. Social media (LinkedIn / Twitter, etc.)

**No dedicated context block.** Raw `social_posts` is in `context` but **not** used by `_build_context_text`. Social reaches the LLM **only via events**:

- Event type: `narrative.social_signal` (executive-relevant new posts).
- In code these are sent as:  
  `title [social]`  
  (Distinct from digital footprint so the LLM can weigh them separately.)

So: **what is sent per social signal** = one line per executive-relevant new post: `"<post summary/title> [social]"` in the Events block.

---

## 6. Reviews (Google reviews for properties)

**Context key used:** `reviews_minimal` — list of `{ display_name, line (sentiment_summary), trend }` per property.

**What the LLM sees:**  
Only when there are **major or significant changes**: a block  
`Review sentiment (sample; significant changes): <display_name>: <line> (trend: <trend>) | ...`  
Significant = declining/negative trend or sentiment line containing negative markers (e.g. complaint, poor, issue). Up to `MAX_REVIEW_PROPERTIES_FOR_SUMMARY` properties (significant ones first).

---

## 7. Events (all types) — the single “Events detected this week” block

**Context key:** `events_this_week`  
This is a list of **all** event dicts (any category/type) detected in the last 7 days. Each event has at least `title`, `type`, and optionally `summary`, `severity`, `category`, etc.

**What the LLM sees:**

- One block:  
  `Events detected this week: <title1> [<type1>]; <title2> [<type2>]; ...`  
- For `narrative.*` types, code replaces the type with the label `[digital footprint]`; all other types are sent as `[<event_type>]` (e.g. `[asset.new_market]`, `[talent.hiring_surge]`, `[partner.major_partnership]`, `[narrative.social_signal]` if you don’t special-case it).
- **Current code** sends **all** events in `events_this_week` (no cap).

So **per signal that produces events**, the LLM gets:

- **Talent:** `title [talent.<type>]` for each talent event.
- **Asset:** `title [asset.<type>]` for each asset event.
- **Partner / capital / public record:** `title [<event_type>]` for each.
- **Digital footprint:** `title [digital footprint]` for each narrative.homepage_updated / narrative.coming_soon.
- **Social:** `title [social]` (secondary; listed after precedent events).

---

## 8. Baseline (shared)

**Context key:** `comparison_baseline_date`  
If set, the LLM sees one line at the top:  
`Comparison baseline date: <date>. All data below is post-baseline: property/role deltas and news are changes or additions since baseline.`

---

## Summary table: what is sent per signal

| Signal            | Context keys used in _build_context_text      | What the LLM actually sees                                                                 |
|-------------------|-----------------------------------------------|---------------------------------------------------------------------------------------------|
| Talent            | jobs_*_since_baseline, jobs_by_function*      | Counts + up to 12 role rows + talent events in Events block as `title [talent.*]`         |
| Asset             | asset_*_since_baseline, asset_delta_by_city  | Counts + delta-by-location (capped in code) + asset events as `title [asset.*]`            |
| Press             | top_news, press_90d                           | “Recent news” block: (date) title [group] for up to 15 items                               |
| Digital footprint | (none; events only)                           | Events block: `title [digital footprint]` per narrative.homepage_updated / coming_soon      |
| Social            | (none; events only)                           | Events block: `title [social]` per narrative.social_signal                                 |
| Reviews           | reviews_minimal                               | Only when significant: “Review sentiment (sample; significant changes):” (up to 10)                                   |
| Other events      | events_this_week                              | Events block: `title [<event_type>]` for partner, capital, public_record, etc.           |

Events are sent without a cap; the full `events_this_week` list is included.
